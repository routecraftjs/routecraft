```ts skip="signature: a type signature, not a statement"
validate<R = Current>(validator: Validator<Current, R> | CallableValidator<Current, R>): RouteBuilder<R>
```

Validate the exchange body using a Validator adapter or callable function. On success the (possibly coerced) return value replaces the body. On failure the adapter throws and the route error handler (if configured) or the default error path handles it.

A validator that returns or throws `refuse(reason, { kind })` refuses the caller rather than failing the instance: the run fails with [`RC5068`](/docs/reference/errors#rc-5068) bound to the route, and a door that dispatched the route (the `http()` source, the ops dispatch mount, an MCP tool call, the ACP mount) answers with the kind and the reason, exactly as it answers a plugin's validate hook. A plain throw stays the instance's failure and reaches a caller as its code alone, so an unexpected error never leaks a reason. The place for this is a rule that needs state the `.input()` schema cannot see: a page that already exists, a classifier's verdict, a record outside the caller's reach. Shape rules belong in [`.input()`](/docs/reference/operations/input), which refuses at the door with the schema's issues, and who may ask in [`.authorize()`](/docs/reference/operations/authorize).

For Standard Schema validation, use the `.schema()` sugar or pass the `schema()` factory.

```ts skip="fragment: not a complete statement on its own"
// Custom validator
.validate((exchange) => {
  if (!exchange.body.email) throw new Error("email required");
  return exchange.body;
})

// Standard Schema via factory
import { schema } from '@routecraft/routecraft'
.validate(schema(z.object({ name: z.string() })))

// A rule that needs state: refuse the caller with a reason a door forwards
import { refuse } from '@routecraft/routecraft'
.enrich(findExistingPage)
.validate((exchange) =>
  exchange.body.existing === undefined
    ? exchange.body
    : refuse("A page with this title already exists.", { kind: "conflict" }),
)
```

The kinds a refusal can carry, and the status or error each door renders them as, are listed on the [plugins reference](/docs/reference/plugins#validate-hooks). A refusal raised inside a nested `direct()` call is that call's failure, never the outer caller's.
