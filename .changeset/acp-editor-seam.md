Talk to a Routecraft agent from your editor, over the Agent Client Protocol (#599, #730, #731, #732).

**`acpPlugin()`** serves the protocol over Streamable HTTP, beside the MCP mount and the HTTP surface, on the same named server and behind the same wall. Nothing ships switched off: installing it serves every agent the context holds, at `/acp` unless `path` says otherwise, and the framework's own name reaches the editor unless `agentInfo` replaces it outright. Options are `path`, `server`, `auth` (the same union `mcpPlugin` takes, `false` to remove the wall), `agent` (the agent a harness serves when it names none), `cors`, `agentInfo` and `toolCallPayloads`. The plugin builds one route per agent when it applies, so it must be listed after the `agentPlugin()` that registers them; an empty registry at that moment fails the build with `RC5003` saying so, rather than serving a protocol with nothing behind it. `@agentclientprotocol/sdk` is an optional peer, loaded through `loadOptionalPeer`, so an app that installs the plugin without it gets `RC5017` naming what to install.

**A conversation is an agent session**, so it outlives the connection, the editor and the instance: closing an editor and reconnecting from another machine reaches the same conversation by its id, `session/load` replays the stored transcript into the editor, one turn runs at a time with the same inbox every other caller of that session gets, and cancelling interrupts the running turn and keeps its partial transcript. **A conversation belongs to the person who started it.** The session record gained `owner`, `cwd` and `title`, and listing, loading and resuming answer only for the caller's own sessions; somebody else's id is answered exactly as a missing one, so probing tells the prober nothing. The management API's listing is deliberately not filtered this way and reports `owner` (replacing the unreleased `startedBy`), because an operator is looking at the instance rather than at their own conversations.

**A person picks the model and the thinking level** from the editor, through the protocol's config options. An agent file offers a choice by writing a list where it would write a value: `model` and `reasoning` each take an ordered list whose first entry is what the agent runs on, with `models` and `reasoningLevels` as the code-side fields. A control with fewer than two choices is not advertised at all, so an agent naming one model and one thinking level shows no pickers rather than two dead ones; `inherit` inside a list is refused naming the entry; a value outside the advertised list is refused with the new `AI1017`. Both stay changeable for the life of the conversation, including while a turn is running, and apply to the next turn rather than the one in flight.

**Which agent answers is not one of them.** A `craft acp` process serves exactly one agent, named by `--agent` or by `acpPlugin({ agent })`, and every session it opens belongs to that agent permanently. Register one editor entry per agent, which is what Zed and JetBrains already support, and the editor's own agent picker becomes the agent picker. A harness never lists, loads, resumes or prompts a session belonging to another agent: it answers such an id exactly as one that was never created. The mount advertises no ACP modes and does not implement `session/set_mode`, so a client calling it gets the protocol's own method-not-found. This is a deliberate position rather than an omission: an agent is an identity, modes are settable at any point in a session, and identity is not a setting. Modes stay free for a future behavioural variation *within* one agent.

**A capability can reach the person's editor.** The new **`surface`** adapter is the one seam for it: `surface(method, params)` is an enricher that asks and waits, which is what an approval is, and `surface.notify(update)` is a destination that tells. Method names and shapes come from the protocol's own generated types rather than being restated, and `sessionId` is filled in from the running turn. It resolves both from the turn's own exchange and, through the correlation id, from a route the turn called, so a capability three hops from the prompt still reaches the person who typed it. `hasSurface(exchange)` is the guard that keeps one route working from an editor and from a schedule alike. Four new codes say which of four different things went wrong: `AI1013` (no surface here), `AI1014` (disconnected mid-turn), `AI1015` (the client never advertised the capability, checked before the call rather than discovered from its silence) and `AI1016` (refused or failed, which is how a person saying no arrives). The framework ships the seam and none of the capabilities that use it: reading a file through the editor is an ordinary route with its own `.authorize()`.

While a turn runs the editor sees token deltas as the model produces them, thinking as thought rather than as text, and every tool call as it starts and when it ends, merged into one stream in order. `toolCallPayloads: false` withholds the arguments and results while keeping the calls themselves visible, which is what an instance serving people other than its operator wants. New events `plugin:acp:connection:opened`, `plugin:acp:connection:closed` and `plugin:acp:session:attached` make the mount observable without reading log lines. Refusals go through the same `bearerChallenge` builder as every other routecraft surface, so a 401 carries the realm and the RFC 9728 `resource_metadata` hint the CLI follows to name the issuer and the missing scope, and rejection log levels match the rest of the codebase: a non-bearer scheme and a stale token are debug, and `warn` keeps meaning a token that failed for a reason worth reading.

**A session is keyed by its id alone.** The agent is an attribute of a conversation rather than part of its identity, so `AgentSessionKey` is the id and `agent` is an ordinary field on the record. It follows the identity rule the framework already uses for an exchange, whose id is a UUID the caller may override through `headers["routecraft.id"]`; `agent(name, { session })` is that override for a conversation, and naming the same id twice continues the same conversation. The management resource answers `GET /ops/agent-sessions/{session}` rather than a pair, and remains the cross-agent view: an operator looking at the instance rather than at one editor's agent.

**One conversation, one agent, for its whole life.** An agent carries a system prompt and a set of tools, so a conversation that changed agent would hand a model a transcript another agent wrote and answers produced with tools it does not have. There is no path to change a conversation's agent: no `setAgent`, no per-session `agent` config option, and no mode. (`acpPlugin({ agent })` still names which agent a mount serves; that is chosen before a session exists, not changed after.) A dispatch whose agent differs from the one the record names is refused with `RC5003` rather than run, and that refusal is now the only rule there is. An agent is never turned into another agent.

**The SQLite session schema is version 2, and prerelease rows are discarded.** Version 1 keyed the table by `(agent, session)`. It reached one published canary and no stable release, so the migration drops and recreates rather than converting: two agents could hold the same session id and neither has a claim on it. **A database written by a 0.7.0 canary or a recent `main` checkout loses its stored conversations on first open.** Nothing released is affected, because no stable release ever wrote this table. Migrations are append-only from here: a schema version identifies one physical schema, so the version 1 entry stays as it shipped.

Also on the session runtime: `interrupt(key)` cancels a running turn and reports whether there was one, and a session records the overrides it is running under so a reconnecting editor sees what it chose.
